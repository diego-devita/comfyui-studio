What it does

  • Runs PRAGMA wal_checkpoint(TRUNCATE) on both SQLite databases (jobs and gallery), merging WAL files into the main .db files
  • Stops any running gallery image downloads

Why it matters

SQLite in WAL mode keeps recent writes in a separate -wal file. If the process is killed before this file is merged back, those writes are lost or the database can become corrupted.

Automatic shutdown

The backend registers a SIGTERM handler that performs this same flush. Docker sends SIGTERM before SIGKILL with a 10-second grace period, so a normal docker stop flushes correctly. On RunPod, pod termination may not deliver SIGTERM reliably or allow enough time.

What can go wrong without flushing

  • Jobs & events database (db/studio.db) — No recovery mechanism. Contains job records (prompt_id, status, params, timestamps) and the activity event log. Recent entries can be permanently lost. In the worst case the DB file becomes unreadable.
  • Gallery database (db/gallery.db) — Has built-in recovery: at startup, if corruption is detected, it deletes the DB and rebuilds from the image files on disk. No real data loss, but the rebuild takes time.
  • Downloads in progress — Interrupted gallery downloads leave partial files. They can be retried.
  • Job output markers (.incomplete files) — If a job was running, the marker stays. Assets page will show an ".incomplete" badge until manually cleaned.
  • Anything else using the DB — Any backend component that writes to SQLite (e.g. model download state tracking) follows the same WAL logic. Unmerged writes in the WAL file are lost if the process dies before checkpoint.

Why timing matters

wal_checkpoint(TRUNCATE) takes an exclusive lock on the database. While it holds the lock, all other writers are blocked. If a write can't complete within busy_timeout (5 seconds), it fails with SQLITE_BUSY.

This means: if a job is being saved, an event emitted, or a gallery image inserted at the exact moment of the checkpoint, that write can fail. The job could end up marked as stalled, an event lost, etc.

Gallery downloads are explicitly stopped by this endpoint. Best to flush when nothing is actively writing: no running jobs, no model/LoRA downloads, no gallery downloads.

When to use

Before stopping or terminating a pod from the RunPod dashboard. Wait for all active operations to finish first.
